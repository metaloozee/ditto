# 006 Codex authentication and credential contract

Status: fixture-backed implementation contract. Ditto hosted authentication, live renewal and account discovery remain blocked. This is not advisor acceptance or PD38 evidence.

Research retrieved public official pages on 2026-10-07. No login, discovery, renewal or inference request was made. No credential files were read. The current docs describe two distinct paths. Their client identities and provider destinations are not interchangeable.

## Known from official sources

1. [Codex authentication](https://developers.openai.com/codex/auth) documents ChatGPT subscription login for Codex applications and automatic token refresh during use. It separately documents API-key billing and enterprise access tokens for trusted automation. It does not establish a client registration, public callback or hosted subscription transport for Ditto. Ditto does not implement an API-key fallback or enterprise-token import.
2. [Sign in with ChatGPT OSS overview](https://developers.openai.com/siwc/token-sharing-open-source/) documents optional ChatGPT plan usage for open-source and locally hosted apps. It directs paid or remotely hosted apps to an interest form. This is evidence about that particular integration, not proof of a general prohibition on all hosted Codex access.
3. [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) describes first registration through `dynamic_agent_client` with the app's actual name and a stable opaque `ext_agent_host_id`. The callback supplies an issued client ID. That issued ID must remain associated with the validated account and must be used for exchange, refresh and later sign-in. It is not another application's static client identity.
4. That OSS flow uses an HTTP loopback callback on `127.0.0.1`. Start the listener first, keep scheme/host/path fixed, allow only the port to vary across attempts, and use the exact attempt URI in authorization and exchange. The documentation explicitly says not to substitute `localhost`. It requires fresh state, nonce and PKCE S256; ID-token JWKS signature, issuer, audience, expiry and nonce validation; returning-account identity checks; and granted `chatgpt.tokens.use.direct` permission. There is no evidence here authorizing replacement with a Ditto public HTTPS callback or device flow.
5. The documented OSS authorization destination is `https://auth.openai.com/api/accounts/authorize`; code exchange and refresh use `https://auth.openai.com/api/accounts/oauth/token` with `resource=https://api.openai.com/v1`. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) requires serialized renewal and atomic replacement of rotating tokens. Use the issued client ID, omit scope on refresh, and keep access, refresh and retained ID tokens protected. Remote revocation uses the discovery document's revocation endpoint. A local disconnect does not prove upstream revocation.
6. [Token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference) describes one-hour access tokens, 30-day rotating refresh tokens, and token-response fields including scope and `earliest_refresh_at`. Those values are documentation claims about this flow, not facts observed with a Ditto account. The fixture's expiry threshold is not a live refresh schedule.
7. [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) documents account-backed `GET https://api.openai.com/v1/models` with the same OAuth access token used for inference. It describes a `models` array, `visibility: "list"`, server ordering, display name and slug. It explicitly distinguishes that response from a bundled/cached Codex app-server catalog. This flow uses the public Responses endpoint, not ChatGPT backend-api. It requires `store: false`, `stream: true` and terminal stream accounting. Account availability and thinking-capability validation for Ditto are still unverified.

## Pinned Pi source findings

Installed from the repository lockfile: `@earendil-works/pi-ai@1.0.1` and `@earendil-works/pi-durable@1.0.1`. No upstream source was changed or imported into product credential code.

- `apps/runtime/node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js` is the legacy Codex adapter. It has a foreign static client ID, a localhost callback, Node HTTP/crypto dependencies and browser/device-code paths. Its refresh attaches that static ID to the legacy token endpoint. Its `toAuth` returns the access token. Neither that identity nor that token-returning interface is used by Ditto.
- `dist/providers/openai-codex.js` labels the provider legacy and uses ChatGPT backend-api with bundled models. This is not account-entitlement evidence and does not establish Ditto authorization.
- `dist/auth/oauth/openai-chatgpt.js` implements the newer dynamic-client OSS flow with Pi's app name, stable host UUID, loopback Node server, issued client ID, direct-use scope and public-resource refresh. It checks ID-token presence but explicitly does not use it for user identity. Ditto must not substitute that presence check for the official account-validation requirements. Its `toAuth` also returns the access token, so it cannot cross the product/runtime boundary.

## Implemented and fixture-tested

The product deployment exports `CodexCredential`, one named SQLite DO per authenticated product user. The runtime and builder/execution code receive no credential namespace or key binding. The credential DO owns encryption, persisted connection/renewal generations and renewal dispatch. It owns no Pi, conversation or execution state.

- `codex-connection.functions.ts` uses the existing Better Auth session seam. Its input is an action, never an owner ID, role, OAuth code or token. Status and disconnect derive the owner from the authenticated session. The pure handler tests use injected authentication, not a real-cookie HTTP claim.
- Connect returns `codex_hosted_auth_unverified`. There is no callback/device/loopback handler, token-upload endpoint or model-request proxy. Expired/reused callback-shaped submissions are rejected as unsupported inputs. There is no claim of an implemented OAuth state machine.
- The synthetic token record contains access, refresh, optional retained identity token and expiry. It is not a validated provider OAuth registration. A future supported flow must add the issued-client, verified-identity, host, scope and timing contract before it can install live credentials.
- Credentials use AES-256-GCM, a fresh 96-bit random nonce and format-2 AAD containing a purpose label, owner, token-record identity, connection generation and expected persisted token-record revision. The SQLite `version` is both projection ordering and the expected revision while connected. Installation seals at version 1; renewal seals at the replacement version and atomically commits that version with ciphertext. The expected revision comes from current SQLite metadata, never from the envelope. This denies ciphertext-only substitution, not whole-database rollback. Access, refresh and retained identity tokens are encrypted together. Each token is bounded to 8192 UTF-8 bytes; the complete JSON/hex envelope must also fit 60,000 characters before installation or replacement may persist. JSON-expanded sets exceeding that total are rejected without truncation or character restrictions. Oversized upstream replacement after rotation clears the spent credentials and requires reconnect. The product-only keyring is `CODEX_CREDENTIAL_KEYS` plus `CODEX_CREDENTIAL_CURRENT_KEY_VERSION`; it does not derive from the authentication or runtime secret. Historical keys remain necessary while records reference them. Missing keys, wrong owner/generation/revision, tampering and unsupported envelope versions fail closed. Previous candidate format-1 envelopes are not accepted by the corrected fixture implementation.
- D1 stores only owner, connection generation, revocation flag, bounded status, projection ordering version and update time. It stores no tokens or credential envelope. Projection writes are update-only, generation-fenced, revocation-fenced and version-ordered.
- Before fixture refresh, SQLite persists a renewal intent and flushes it. Fresh D1 authority and the current DO generation are checked immediately before dispatch and again before accepting replacement. A competing workspace request sees renewing, rather than spending a second token. The complete rotated token set is replaced in one synchronous SQLite transaction.
- Disconnect commits the D1 fence first, then hands the new revoked generation to the DO. Either fence denies further renewal. A late result cannot overwrite explicit reconnect or recreate deleted D1 state. D1 checks have no authority cache.
- On activation, a retained renewing intent becomes reconnect-required and its encrypted token set is cleared. An ambiguous response or a failure after upstream rotation also requires explicit reconnect. The code makes no exactly-once claim and never blindly retries a possibly spent refresh token.
- Production renewal and fixture installation are disabled by runtime gates, not TypeScript visibility alone. Keyring and storage helpers use JavaScript private methods and are unreachable by RPC. A standalone production-class RPC test verifies that private helper names fail and even a direct call to the fixture installation method cannot install credentials. Only the isolated test subclass can install synthetic tokens or fetch the fixed `.invalid` renewal fixture. Fetch executes inside that credential DO, with mocked networking or the standalone Miniflare outbound fixture. No token leaves through a status or renewal result.

## Externally unverified and blocked

- Ditto's exact authorized hosted client registration, callback or device flow, and provider approval/support for this hosted application.
- Which subscription transport and account-backed capability contract Ditto should use. The newer OSS Responses flow and the legacy Codex backend flow must not be combined by assumption.
- Actual token lifecycle, earliest-refresh timing, revocation confirmation, safe reconciliation after a lost rotation response, account entitlements and thinking options for a connected Ditto user.
- Hosted Worker eviction, deployment/update behavior, service-binding caller identity, provider networking, quotas and billing.
- Real-cookie HTTP smoke coverage for the new server function. Existing product authentication is reused, but the new ownership tests inject identity.

PD38 remains `not run`: no approval for live credentials, provider usage or hosted validation. Plans 007 and later still need their own request/admission/discovery implementation. No retained workspace, UI, model engine, API-billing fallback or deployment is enabled by this change.

## Cloudflare and test compatibility sources

- [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) documents synchronous SQL and `transactionSync` rollback, with no asynchronous transaction callback.
- [Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/) documents binding-based composition, secret protection and bounded request handling.
- [Vitest integration](https://developers.cloudflare.com/workers/testing/vitest-integration/) and [test APIs](https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/) were read. Current docs have APIs newer than the pinned pool. Installed source/types and actual workerd tests decide the usable local contract.
- `npm view @cloudflare/vitest-pool-workers@0.12.21 peerDependencies --json` returned Vitest, runner and snapshot support for `2.0.x - 3.2.x`. Web's locked Vitest is 4.1.10. `apps/credential-tests` therefore pins Vitest/runner/snapshot 3.2.7, pool 0.12.21, Miniflare 4.20260310.0 and compatibility date 2026-03-10. It imports only the product credential implementation. It does not upgrade web Vitest or put the DO in the runtime.
- Pool tests cannot cleanly observe `ctx.abort` because abort also produces unhandled reset events in that runner. A separate Node test uses standalone Miniflare/workerd with the same product DO and real SQLite. It proves actual abort after rotation, two reactivations without redispatch, and survival of a successfully committed replacement after another abort. No runner-wide suppression is configured.
