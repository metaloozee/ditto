## Required authority

Open one short `git_transport` operation after all local checks and secret
preflight pass. Bind it to:

- workspace-session identity and lifecycle generation
- owned GitHub repository and installation
- operation type `push`
- exact `refs/heads/<session-branch>`
- exact preflight local HEAD SHA
- contract version, expiry, and one receive-pack exchange

No token is minted until the broker validates a request against this record.

## Protocol work

Use the official protocol grammar:

- https://git-scm.com/docs/gitprotocol-http
- https://git-scm.com/docs/gitprotocol-pack
- https://git-scm.com/docs/gitprotocol-capabilities

Implement and test these phases:

1. Bound and validate receive-pack ref discovery for the exact repository.
2. Record the advertised old object ID for the exact target ref in the open
   operation. Reject duplicate or conflicting discovery.
3. Accept one receive-pack POST. Parse only the bounded pkt-line command prefix
   before the pack stream.
4. Require exactly one create or update command for the target ref. Require the
   new object ID to equal the operation's preflight HEAD.
5. Reject zero object IDs used for deletion, extra refs, push certificates,
   push options, unknown or malformed capabilities, protocol downgrade,
   alternate hash widths, and a mismatched advertised old object ID.
6. Reconstruct a fresh streamed upstream body from the validated prefix and the
   remaining pack stream. Do not buffer the pack.
7. Mint the installation token, construct a fresh HTTPS request, set
   `redirect: "manual"`, and stream the response with bounded headers.
8. Parse the bounded report-status response enough to require `unpack ok` and
   success for only the expected ref.
9. Close and consume the operation on every terminal path.

## Force-update feasibility gate

Git's wire command contains old object ID, new object ID, and ref name. It does
not contain a trustworthy "force" flag. The broker cannot prove ancestry from
those IDs unless it can validate the commit graph or rely on a GitHub operation
that rejects non-fast-forward updates.

Before enabling push, prove one safe method with an integration test against an
unprotected test branch. The test must attempt a crafted non-fast-forward
receive-pack request, not only `git push` without `--force`.

If the broker cannot prove rejection, follow the spec and disable push. Keep
local commits and secret preflight. Update UI and agent tools to report that
push is unavailable. Do not infer safety from the baked Git client because the
sandbox is untrusted. Any temporary-ref or GitHub REST alternative changes the
approved contract and requires a spec revision before implementation.

## Tests

Add parser fixtures generated by Git, then include hostile mutations:

- valid branch creation and fast-forward update
- deletion, extra ref, wrong branch, wrong new SHA, wrong old SHA
- truncated or overflowing pkt-line length
- duplicate command, push certificate, push options, unknown capability
- oversized prefix and oversized response status
- redirect and credential-shaped caller headers
- concurrent second receive-pack request
- crafted non-fast-forward request against an unprotected integration branch
- token absence from sandbox environment, argv, files, jobs, logs, and errors
- existing exact-SHA staging and Git secret preflight still execute before the
  operation opens

## Done criteria

- No GitHub installation token enters a sandbox process.
- Fetch and enabled push use exact broker contracts.
- Push permits one target ref and one serialized receive-pack exchange.
- Non-fast-forward updates are either proved rejected or push is disabled.
- Pull-request creation remains Worker-owned through Octokit.

## Maintenance note

Regenerate protocol fixtures when the image Git version changes. Keep old
contract versions only while a deployed image can still emit them.

## Stop conditions

- If checking non-fast-forward ancestry requires trusting the sandbox, stop and
  disable push.
- If validating the request requires buffering the packfile, stop and disable
  push.
- If Git emits a required capability outside the reviewed allowlist, stop and
  version the contract. Do not accept unknown capabilities.
