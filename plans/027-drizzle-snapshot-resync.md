## Why this matters

Drizzle generates a migration by diffing `apps/web/src/db/schema.ts` against the newest snapshot, `apps/web/migrations/meta/0027_snapshot.json`. Plan 023 added the table `candidate_capacity_claims` and CHECK constraints to `schema.ts` so it matches the real migrated database. The 0027 snapshot predates that change. A plain `pnpm --filter @ditto/web db:generate` now emits:

- `CREATE TABLE candidate_capacity_claims`, which fails on apply because `0025_candidate_capacity.sql` already created it;
- table rebuilds (`CREATE TABLE __new_x`, copy, `DROP TABLE x`, rename) for `candidate_command_decisions`, `candidate_archives`, `candidate_continuations`, `candidate_restore_barriers` and `model_request_admissions`. `DROP TABLE` deletes a table's triggers, so the hand-written `*_final` triggers would silently vanish.

The fix is to regenerate the 0027 snapshot from the aligned `schema.ts`, keeping its `id` and `prevId` so the chain is unchanged. This repeats commit `cf017e7`, which added `0026_snapshot.json` the same way ("Snapshot generated by drizzle-kit from schema.ts ... no SQL or journal change").

Separately, `scripts/check-schema-drift.mjs` (added by 023) only rejects real-database triggers that are *not* allowlisted. It does not notice when an allowlisted trigger is *missing* from the real database, which is exactly what a bad rebuild migration would cause. Close that gap.

## Maintenance notes
- After this lands, `db:generate` is safe again for ordinary schema changes. If a future schema change makes Drizzle rebuild a table with a `*_final` trigger, the generated migration drops that trigger. `pnpm db:drift` now fails on that, and the author must recreate the trigger in a migration Drizzle generates with `--custom`.
