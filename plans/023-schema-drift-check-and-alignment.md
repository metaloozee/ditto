Migration files are generated by Drizzle. **Never create, edit, rename, trim or delete anything under `apps/web/migrations/`**, including `meta/`. ## Why this matters

Migrations 0022–0026 were written by hand. `apps/web/src/db/schema.ts` doesn't describe everything they create. On 2026-10-24 the maintainer repaired Drizzle's snapshot chain: `meta/0026_snapshot.json` was generated from `schema.ts`, so Drizzle's idea of the database is `schema.ts`, not the real tables. A structural comparison of the two found:

- `candidate_capacity_claims` exists in the database (created by `0025_candidate_capacity.sql`) but has no table in `schema.ts`.
- CHECK constraints exist in the SQL but not in `schema.ts` for `candidate_archives`, `candidate_continuations`, `candidate_restore_barriers` and `model_request_admissions`. `candidate_command_decisions` has its checks split differently (five in SQL, two combined in `schema.ts`).
- Uniqueness is declared inline in SQL (`UNIQUE` on a column, which SQLite stores as an `sqlite_autoindex_*`) but as named unique indexes in `schema.ts`. These are semantically equal.
- Four triggers exist that Drizzle can't model: `candidate_capacity_claims_final`, `candidate_archives_final`, `candidate_continuations_final`, `candidate_restore_barriers_final`.

If someone adds `candidate_capacity_claims` to `schema.ts` without care, `db:generate` emits `CREATE TABLE` for a table that already exists, and the migration fails on apply. Nothing currently detects this.

## Steps

### Step 1: Baseline
Install, then run `pnpm typecheck`, `pnpm test` and `pnpm check`. Record the results.

### Step 2: Write the drift check
`scripts/check-schema-drift.mjs`:
1. **Real DB (A):** read `apps/web/migrations/meta/_journal.json`. For each entry in order, read `apps/web/migrations/<tag>.sql`, split it on `--> statement-breakpoint`, and run each non-empty part with `db.exec` on a `new DatabaseSync(":memory:")`.
2. **Schema DB (B):** create a temp directory with `fs.mkdtempSync(path.join(os.tmpdir(), "ditto-drift-"))`. Run `pnpm --filter @ditto/web exec drizzle-kit generate --dialect=sqlite --schema=./src/db/schema.ts --out=<tmp> --name=drift` with `execFileSync` (cwd = repo root). This writes one full-schema `0000_drift.sql` into the empty temp dir. Apply it the same way to a second memory DB, and remove the temp dir in `finally`. If the CLI rejects these flags, STOP and report its output. Don't point `--out` inside the repo.
3. **Shape per table** (skip `sqlite_%` and `_cf_%`):
   - columns from `pragma table_info` (name, type uppercased, notnull, dflt_value, pk);
   - **unique column sets** from `pragma index_list` rows with `unique=1`, including autoindexes, each as its sorted column list (so inline UNIQUE equals a named unique index);
   - non-unique indexes as `name:cols`;
   - foreign keys from `pragma foreign_key_list` (table, from, to, on_update, on_delete);
   - CHECK expressions extracted from `sqlite_master.sql`, normalized by lowercasing, removing whitespace, quotes and backticks, and stripping `<table>.` qualifiers.
4. **Triggers:** names from `sqlite_master` where `type='trigger'`. A trigger present in A is accepted only if listed in `scripts/schema-drift-allowlist.json` (`{"triggers": [...]}`, initially the four names above). Any trigger in B is a difference.
5. Print each difference as `table.kind: real=… schema=…`. Exit 1 if there are any; otherwise print `no drift` and exit 0.

Add `"db:drift": "node scripts/check-schema-drift.mjs"` to root `package.json`, and insert `pnpm db:drift &&` after `pnpm check &&` in `verify`.

**Verify**: `pnpm db:drift` exits 1. Its output must list exactly the drift in "Why this matters" (the missing table and the CHECK differences). Paste the output into the evidence file. If it reports any other kind of difference, STOP and report it. Don't widen normalization to hide it.

### Step 3: Align `schema.ts`
- Add `candidateCapacityClaims` (`sqliteTable("candidate_capacity_claims", …)`) matching 0025: columns, the five column-level and two table-level CHECKs, `uniqueIndex("candidate_capacity_claims_owner_uidx").on(table.kind, table.ownerKey)` and `index("candidate_capacity_claims_live_idx").on(table.pool, table.state, table.userId)`. Name each check descriptively, as existing checks are named. Don't export or use it anywhere else.
- Add or adjust CHECKs on `candidate_archives`, `candidate_continuations`, `candidate_restore_barriers`, `model_request_admissions` and `candidate_command_decisions`, so the normalized expressions equal the SQL's exactly. Split or merge checks to match the real count and text.
- Leave the uniqueness representation alone unless the check still reports it.

**Verify**: `pnpm db:drift` prints `no drift`; `pnpm typecheck` and `pnpm test` pass. If a difference can't be closed without changing a real constraint's meaning, STOP.

### Step 4: Report Drizzle's view (don't install anything)
The schema now describes objects that already exist, so a normal `db:generate` in the repo would emit DDL for them. **Don't run it in this checkout.** Instead:
1. Create a scratch worktree with `git worktree add --detach /home/ayan/ditto-execution/drift-scratch HEAD`. Copy your edited `schema.ts` into it, and run `pnpm install --frozen-lockfile` inside it. **Never symlink `node_modules` from another checkout.**
2. In the scratch tree, run `pnpm --filter @ditto/web db:generate --name=drift_resync`. Record the generated SQL file's statements, by kind and target, and the new snapshot's name and `prevId`.
3. Remove the scratch worktree with `git worktree remove --force /home/ayan/ditto-execution/drift-scratch`.

**Verify**: the evidence file lists Drizzle's would-be statements. Every statement must target an object the real migrations already create. If any statement targets something new, STOP and report it.

### Step 5: Gates and evidence
Run `pnpm check`, `pnpm typecheck`, `pnpm test` and `pnpm db:drift`. Write `plans/evidence/023-schema-drift.md` with: the check's design, its Step 2 output, the `schema.ts` changes, the Step 4 report, and gate results.
